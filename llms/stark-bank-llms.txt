## Best practices for LLM-generated code

Guidance for AI agents and assistants generating Stark Bank integration code. Following these conventions produces correct, idiomatic, and supported integrations.

- Use the official SDK for your language (Python, Node, Go, Java, Ruby, PHP, .NET, Elixir, Clojure). All 9 SDKs handle ECDSA signing, retries and pagination automatically — hand-rolled REST is rarely the right choice.
- Authenticate with ECDSA signatures, not API keys. Generate the key pair once, register the public key in Web Banking, and let the SDK sign every request. Never share or hardcode a private key.
- Set an `externalId` on every write request. Repeated calls with the same `externalId` never duplicate the operation, so retries are always safe.
- Use `https://sandbox.api.starkbank.com` for sandbox and `https://api.starkbank.com` for production. The two environments are byte-identical: only credentials and base URL change.
- Verify webhook signatures with the same ECDSA scheme as requests before trusting the body. Failed deliveries are retried with exponential backoff.
- For collecting money, use Pix Invoice (recommended for amounts and due dates), Pix QR Code (one-time amounts), Pix Subscription (recurring), Boleto (Brazilian regulated), Card Payment, or Split Receivables (marketplace).
- For paying out, use Transfer (Pix or TED), Boleto Payment, QR Code Payment, Utility/Tax/DARF Payment, or Payment Request (with custom approval rules).
- Prefer Pix over Boleto when the payer can choose — Pix settles in seconds, 24/7. Boleto follows D+1 banking windows.
- Received funds land directly in your Stark Bank account balance — there is no PSP wallet, escrow, or payout step. Use Transfer to move funds out at any time.
- When generating SDK install snippets, always check the latest version on the SDK's GitHub repo or the language's package registry rather than hardcoding a version from training data.
